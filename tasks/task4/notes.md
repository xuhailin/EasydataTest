# Task 4 学习笔记：文档分块、SQL × AI 与个人心得

记录日期：2026-09-17。

本记录根据用户对 I3 六道思考题的回答及本次讲解整理。“原始理解”保留用户表达的要点，“知识补充”为助手整理，不作为用户个人心得。2026-09-20 根据用户提供的心得原文，补充文档分块、向量模型选型及 AI Functions 的学习整理；概念校正单独列出。

## 1. 为什么 AI_COMPLETE 出现在 UPDATE 中会放大事务风险？

**原始理解：** AI_COMPLETE 是外部模型调用，事务持续时间不可控，数据来源容易失去约束，失败回滚成本也高。

**知识补充：** 等待外部模型会延长事务及锁的持有时间，占用数据库连接和执行资源，影响其他请求。更关键的是：数据库回滚能撤销写入，却不能撤销已经发生的模型推理、网络请求和费用。多行更新后续失败时，前面已经发生的模型调用仍然有成本；重新执行还可能得到不同结果。

“数据来源失去约束”可以具体落到模型输出的来源、格式与业务有效性校验，但不是本题的核心事务风险。

通常可以拆成：短事务固化输入及版本 → 事务外调用模型 → 校验结果 → 短事务核对输入版本并写回。若源数据已变更，应按业务规则丢弃旧结果或重新处理，避免覆盖新内容。

## 2. 同一查询向量为什么应先保存到变量或中间结果？

**原始理解：** 可重复使用，节省 Token，也可保证多次匹配使用一致的向量。

**知识补充：** 核心是只计算一次、重复使用，避免同一语句多处求值造成重复模型请求，减少调用费用和延迟，并确保各处复用同一个查询向量。“节省 Token”取决于服务的计费方式，更一般的说法是减少重复推理与计费。

## 3. Rerank 对象数组为什么要保留 ID、版本和权限字段？

**原始理解：** ID 可以追溯具体内容；版本用于避免旧结果与更新后的数据不一致；权限字段确保结果使用时仍有限制，不能在查询过程中丢失权限约束。

**知识补充：**

- ID：把重排分数关联回正确的原始记录，支持引用与追溯。
- 版本：用于检查评分对应的内容与最终使用的内容是否一致。例如评分针对文档 v1，取正文时已更新为 v2，不能直接把旧评分当成对新内容的判断。保留版本本身不会自动保证一致性，还要实际核对和处理版本冲突。
- 权限：保留后续校验所需的业务信息，但权限标签本身不等于权限执行。在发送给重排模型前就应过滤无权访问的内容，最终使用时还需按当前权限校验。

Rerank 通常比较查询与候选文本，而不是给旧向量再次排序；需要关注的是候选内容、评分、版本及最终引用之间的对应关系。

## 4. 数据库内部重试和应用重试叠加会产生什么后果？

**原始理解：** 重复执行会增大 Token 消耗，可能产生重复数据，也可能一直互相重试。

**知识补充：** 两层重试可能相乘，放大请求数、费用与延迟，并加重模型服务的限流或拥塞。例如，应用最多尝试 3 次，每次数据库内部最多尝试 3 次，则单个模型调用最多可能发生 9 次。这里的“尝试次数”包含首次调用。

是否产生重复数据，取决于写入是否幂等、之前是否已提交及如何恢复；不能把重复推理直接等同于重复记录。有明确上限时也不会无限重试，但嵌套重试会让总体预算更难控制。

应统一最大尝试次数、总时间与费用预算，并通过幂等键、任务状态和恢复点处理重复执行。数据库写入幂等也不代表外部模型只会推理或计费一次。

## 5. 哪些模型配置变化会迫使你重算历史数据？

**原始理解：** 模型更换、版本升级、维度变化，以及其他导致向量结果偏差较大的变化，都可能需要重算。

**知识补充：** 判断依据是历史结果是否仍兼容、是否满足新的处理要求，而不是只看数值偏差大小。需要区分不同派生数据。

| 变化 | 对历史数据的影响 |
| --- | --- |
| Embedding 模型或不兼容版本变化 | 通常需要重算历史文档向量；即使维度相同，也可能已属于不同向量空间 |
| Embedding 输出维度变化 | 需要使历史向量、向量列和索引匹配目标维度 |
| Embedding 输入预处理、截断规则或任务指令变化 | 若要求历史数据采用新规则，需要重新生成受影响的向量 |
| Rerank 模型变化 | 需要重新评测排序和阈值；若保存了旧分数且要求新口径，需重新评分，不必因此重算文档向量 |
| 摘要或抽取的模型、Prompt、输出要求变化 | 若历史结果也必须满足新要求，需要重新生成或处理受影响的结果 |
| 仅更换密钥，实际模型与处理规则不变 | 通常不需要重算 |

模型升级若明确保证兼容，可以例外；更换服务端点也要核对背后的实际模型和处理规则，不能只根据逻辑模型名未变就认定结果兼容。

## 6. 什么情况下直接使用模型 SDK 比 AI Functions 更合理？

**原始理解：** 调用量很大、AI Functions 开销过大，或者对数据安全和权限要求较高时，可以考虑 SDK。

**知识补充：** 大规模或长时间任务使用 SDK 配合应用层任务系统，通常更便于批处理、并发控制、断点恢复和独立扩容，也可避免长时间占用数据库执行资源。需要流式输出、复杂工具调用、多轮编排、模型路由或应用层熔断时，也更适合在应用侧组织调用；具体能力仍需核对所用版本。

不能只因为安全要求高，就认定 SDK 更合适。SDK 不天然更安全，AI Functions 也可以利用数据库权限与审计。两种方式都需要落实权限过滤、脱敏、凭据管理和数据出域控制，应判断哪种架构能满足具体要求。

## 个人心得体会

记录日期：2026-09-20。以下根据用户本次提供的心得整理，修正错别字与表述，保留原文重点；不新增个人经历或实践结论。

### 1. 为什么要切分文档？

一份长文档可能包含多个话题，单个向量很难同时准确表达所有内容。如果检索命中后把全文都交给模型，不仅会增加 Token 消耗，还可能让无关内容干扰模型对关键证据的关注。

因此，可以把文档切成语义相对完整的小片段，让用于检索的片段单独向量化、单独存储，便于定位与问题相关的内容。

### 2. 如何切分文档？

切分时既要让片段便于检索，也要尽量保留理解它所需的上下文。我关注的原则包括：

- 优先沿标题、段落等语义边界切分，尽量避免从句子中间断开。
- 控制片段长度。课程提到的 500～800 字可作为起始参考，再根据文档特点和检索效果调整。
- 适当保留重叠。可以参考相邻片段重叠 50～100 字，减少边界处的信息断裂。
- 保留元数据，让片段能够关联回原始文档，并支持后续过滤与追溯。

### 3. 三种分块方式及其取舍

| 方式 | 核心做法 | 适用场景与成本 |
| --- | --- | --- |
| 基于 Embedding 的语义分块 | 先分句，再计算句子向量，根据相邻句子的语义变化决定分块边界 | 可用于结构不清晰、话题跳跃的长文，但需要额外的向量计算 |
| 动态重叠 | 保持块大小基本不变，根据内容和边界特征调整重叠量 | 可用于改善边界信息缺失；基于结构规则实现时，额外计算成本较低 |
| 父子 Chunk | 子块建立向量索引，命中后通过关联关系取回父块 | 用较小片段定位内容，用较大片段提供更完整的上下文，适合回答依赖上下文的场景 |

### 4. 向量模型如何选型？

选型要结合知识库本身的特点，考虑语言、多模态支持、成本和延迟。需要先弄清楚知识库主要是什么内容，是否包含大量 PDF、图表或扫描件，再结合数据规模、调用量和响应速度要求做选择。

### 5. 对 AI 原生数据库与 AI Functions 的理解

我关注的是数据库如何把 AI 应用需要的数据管理、检索与模型调用能力纳入自身架构，让这些能力能在数据处理流程中直接使用。

课程中的 seekdb AI Functions 对应了几类常用操作：

| 函数 | 作用 | 课程所述的执行方式 |
| --- | --- | --- |
| `AI_EMBED` | 把文本转成向量 | 调用外部模型服务 |
| `AI_RERANK` | 对候选内容进行相关性重排 | 调用外部模型服务 |
| `AI_COMPLETE` | 生成、摘要、分类或抽取 | 调用外部模型服务 |
| `AI_PROMPT` | 根据模板和参数组装 Prompt | 本地组装，不调用模型 |

前三个函数虽然可以写在 SQL 中，但仍涉及外部网络调用，因此需要考虑数据安全、网络延迟、失败和重试成本。等待模型可能延长事务及锁的持有时间；数据库回滚可以撤销数据写入，却无法撤销已经发生的模型推理和费用。

### 6. 实际使用时，先缩小数据范围

我认为应尽量先过滤，再调用模型，让 AI 函数处理已经缩小的集合。这样可以减少无关数据参与处理，降低 Token 消耗和延迟，也更容易控制调用规模。

## 本次心得的概念校正与补充

以下为助手核对课程后的补充，与用户个人心得区分记录。

1. **分块参数是起点，不是固定标准。** 500～800 字、50～100 字重叠来自课程建议，应按文档结构、模型输入限制与实际检索效果调整；字符数也不等于 Token 数。
2. **语义分块有不同实现。** 上文描述的是课程中基于句子 Embedding 的方式。每个句子需要向量，不等于每句必须单独发一次网络请求；是否支持批量取决于接口和实现，成本还包括额外计算与后续块向量生成。
3. **动态重叠和父子块也有代价。** 增加重叠会增加重复内容、存储与向量化工作；取回父块可能增加生成阶段的上下文和 Token 消耗。它们都需要结合效果验证，不能保证必然提升。
4. **PDF 处理不只取决于向量模型。** 扫描件、图表还涉及 OCR、版面解析或多模态处理；应先确定如何保留内容，再选择检索表示和模型。
5. **“AI 原生”关注能力与数据流。** 不能仅理解为从零以大模型为核心重写数据库，也不表示模型推理就在数据库进程内执行。原文“数据库事务的不一致性”在此更准确的表述是：外部推理不受数据库事务回滚保护，不等于数据库自身的事务一致性失效。
6. **先过滤要落实到执行过程。** 不能仅凭 SQL 的书写顺序推断 AI 函数一定最后执行；必要时用拆分语句、任务表或明确物化的中间结果，确保只有经过业务与权限过滤的数据进入模型调用。
