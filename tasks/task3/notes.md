## 1. 为什么同一批向量换一种距离函数后，排序可能完全不同？

**原始理解：** 距离函数考虑长度和方向的不同组合，应该匹配生成向量时采用的模型与度量，不能随意更换。

**知识补充：** 是有些距离函数只比较方向，而不是有些向量只有方向。

| 度量 | 比较什么 | 排序规则 |
| --- | --- | --- |
| 余弦相似度 | 非零向量的方向，不受长度影响 | 越大越相似 |
| 点积 | 方向与长度的组合 | 越大越相似 |
| 欧氏距离（L2） | 两个点的实际距离，受方向与长度影响 | 越小越相似 |

例：查询 q = (1, 0)，候选 A = (10, 0)，B = (1, 1)。余弦相似度分别为 1 和约 0.707，因此 A 在前；欧氏距离分别为 9 和 1，因此 B 在前。

选择度量时应匹配模型训练方式、模型说明及归一化规则。若查询与候选都归一化为单位长度，则点积等于余弦相似度，L2 距离的平方等于 2 − 2 × 余弦相似度，三者排序一致（忽略并列顺序及数值误差）。不同模型、度量下的分数阈值不能直接照搬。

## 2. 精确 KNN 为什么仍是 ANN 评测的重要基线？

**原始理解：** 需要同时关注高召回率和低延迟，不能一味为了速度牺牲召回。

**知识补充：** 精确 KNN 给出指定向量度量下真正的 Top-K，作为参照，才能衡量 ANN 漏掉多少近邻、提速付出了多少召回损失。

例如：同一查询、同一数据快照、同一距离函数、同一权限条件下，精确 KNN 返回 10 条，ANN 返回的 10 条中有 8 条与之重合，则该查询的 ANN Recall@10 为 8 / 10 = 80%。该示例假设至少有 10 条可访问数据，且不存在影响集合比较的边界并列。

要区分两种召回口径：

- ANN 近邻召回：对照精确 Top-K，检查近似搜索是否漏掉本应找到的近邻。
- 业务相关性召回：对照人工标注的相关证据，检查是否找到回答问题需要的内容。

向量距离最近，不保证业务上最相关或最有用。ANN 的评测还应结合延迟、吞吐和资源成本。

## 3. “先向量检索再做权限过滤”会产生哪些正确性和安全问题？

**原始理解：** 检索到的 Top-K 可能全部被权限过滤掉，最后返回空结果。

**知识补充：**

- 正确性：全库 Top-10 都无权访问，过滤后为空；但排名第 11～20 的内容可能相关且可访问，却没有被取到。因此不能把“全库 Top-K 后过滤”等同于“在可访问范围内找 Top-K”。
- 安全性：如果权限过滤前的内容进入模型上下文、用户可见摘要、共享缓存或不适当的日志，就可能泄露信息。后过滤不必然泄露，但必须确保过滤前的数据不越过权限边界。
- 处理原则：在检索阶段可靠地限制可访问范围，并在交给模型前校验最终证据权限；权限更新、缓存和异步同步也必须受控。

扩大候选数量可能缓解过滤后的结果不足，但不能保证找到可访问范围内的正确 Top-K，也不能代替权限控制。

## 4. 为什么 Embedding 模型升级通常需要重建历史向量？

**原始理解：** 不同模型版本生成的向量不同。

**知识补充：** 关键在于新旧模型通常不共享可直接比较的语义空间。即使维度相同，各坐标的含义也可能改变；不能直接用新模型生成的查询向量去检索旧模型生成的文档向量。

可以类比两张使用不同坐标规则的地图：一张图中的坐标，不能直接拿到另一张图中找位置。

通常应使用新模型重新计算历史文档向量、重建索引，并让查询与文档使用配套的模型及输入处理规则。明确保证向量空间兼容的升级可以例外。迁移时记录模型、版本、维度和原文版本，有助于校验、切换和回滚。

## 5. 检索 Recall 提升后，最终答案质量为什么可能没有同步提升？

**原始理解：** 最终答案还与证据权限等因素相关，不能只由召回这一步决定。

**知识补充：**

- 证据本身可能过期、不完整或互相矛盾。
- 召回的证据可能无权使用，被后续过滤。
- 重排可能把关键证据放在后面，最终因上下文长度限制被截断。
- 更多候选可能引入重复和噪声，干扰模型。
- 即使证据齐全，模型仍可能理解错误、遗漏条件或引用错误。

因此，找到证据、把证据送进上下文、正确使用证据是三个不同环节。评测既要看检索指标，也要看最终答案的忠实度、相关性、完整性和引用准确性。

## 6. 专用向量数据库的收益是否足以覆盖新增系统成本？

**用户最初的疑问：** 不理解这道题在问什么。

**知识补充：** 这题是在问：为了向量检索，多维护一套数据库是否值得？

| 方案 | 可能的收益 | 需要承担或验证的成本 |
| --- | --- | --- |
| 在现有数据库中扩展向量能力 | 复用部署、备份、业务数据及权限信息，减少跨系统同步 | 验证检索性能、索引和过滤能力能否满足负载 |
| 单独部署专用向量数据库 | 可能提供更适合当前负载的索引、吞吐与独立扩容能力 | 新增部署、监控、备份、故障恢复，以及数据和权限同步 |

例如，业务库已撤销某文档权限，而向量库尚未同步，这段时间如何保证安全，也是系统成本的一部分。

判断顺序：先明确向量规模、增长、并发、延迟、召回、更新和权限要求，再实测现有方案是否满足；如果有明显瓶颈，再验证专用系统的收益是否覆盖新增成本。不能仅凭“专用”认定性能更好，也不能仅凭向量数量决定选型。

**当前结论边界：** 本次没有给出具体业务负载和实测结果，因此不替用户判断其场景应选哪一种数据库。

## 7. 追问：KNN 和 ANN 需要一起工作吗？

KNN（K-Nearest Neighbors，K 近邻）在这里指找出与查询最近的 K 条向量；精确 KNN 要求结果精确。ANN（Approximate Nearest Neighbor，近似最近邻）允许少量遗漏，以减少搜索开销。这里讨论的是向量检索，不是 KNN 分类算法。

**不要求每次查询同时运行两套搜索。** 常见配合有以下三种。

### 7.1 离线评测：精确 KNN 当参照，ANN 接受比较

1. 在同一数据快照、度量和权限范围下准备一批查询。
2. 对每条查询分别运行精确 KNN 与 ANN。
3. 比较结果重合率、耗时及资源消耗。
4. 调整 ANN 索引或搜索参数，选出满足业务要求的配置。

精确 KNN 可以运行在评测环境中，不必随每一次线上请求运行。

### 7.2 在线检索：ANN 找候选，可选地精确计算候选距离

假设在 100 万条可访问向量中要返回 Top-10：

```text
查询向量
  → ANN 在允许访问的数据范围内搜索，返回 100 个候选
  → 可选：用原始向量精确计算这 100 条的距离
  → 按距离排序，选出 10 条
  → 校验最终证据权限，供后续 RAG 使用
```

100 万、100 和 10 仅用于说明流程，不是推荐参数。候选精确计算常用于修正量化或近似分数；如果 ANN 已经使用同一原始向量和度量精确打分，再计算一次可能没有收益，具体取决于索引实现。

**这只能保证候选集合内排序精确，不能保证全库精确 Top-10。** 如果真正最近的一条没有进入候选集合，后续重排无法把它找回来。因此“ANN + 候选精排”不能直接等同于全库精确 KNN。

这里的精确距离重排，也不同于用 Reranker 模型重新判断问题与文本的业务相关性。

### 7.3 按查询选择：小集合用精确搜索，大集合用 ANN

应用或数据库也可以按负载选择搜索方式。例如，权限与业务条件过滤后只剩几百条时，可以精确计算；可访问集合很大时，可以使用 ANN。具体是否自动选择、何时切换，取决于数据库实现和实测结果。

**一句话总结：精确 KNN 可以负责评测参照和小集合检索，ANN 可以负责大集合的快速检索；是否协作取决于场景，并非固定串行步骤。**

## 8. RAG 的边界、流程与评估

记录日期：2026-09-16。根据用户本次提交的笔记整理，保留“数据边界”“数据准备 + 在线查询 + 评估反馈”“按环节定位问题”的主要理解。概念修正与额外说明集中列在文末，不将助手补充写成用户个人体会，也不据此认定课程或实践全部完成。

### 一、为什么需要 RAG？

模型训练数据通常不包含企业内部的私域知识；模型参数中的知识存在时间边界，无法仅靠参数获知最新事实；仅凭模型参数生成的答案，也难以核验具体事实来自哪里。

RAG（检索增强生成）的基本做法是：回答之前，先从外部数据源获取相关证据，再让模型结合证据生成答案。要让答案可追溯，还需要保存原文、来源、版本，并建立引用和校验机制。

### 二、开始之前，先明确数据边界

1. **找什么？** 需要哪些事实、文档或业务信息，哪些内容不在范围内。
2. **去哪里找？** 知识库、数据库、网页，还是业务 API。
3. **何时找？** 哪些资料可以提前入库，哪些信息必须在查询时获取；资料如何刷新。
4. **找到多个结果怎么合并？** 如何去重、排序、保留上下文，并处理来源或版本冲突。
5. **找不到怎么办？** 澄清问题、改写查询、换来源补搜，或在证据不足时明确说明无法回答。
6. **数据能给谁看？** 明确租户、用户和角色权限，让权限约束贯穿检索、上下文与输出。

这些问题决定系统的检索范围、处理方式和失败时的行为，应在设计具体流程之前明确。

### 三、整体流程：数据准备 + 在线查询 + 评估反馈

这个三部分划分可以保留，同时把更细的环节放到各自下面。

#### 1. 数据准备：把资料变成可检索、可核验的证据

这是写入和维护数据的过程，通常在用户查询之外完成，也需要持续更新。

1. 解析 Markdown、网页、PDF 等来源，保留原文、标题、章节和来源位置。
2. 清理空内容、重复内容与噪声，按业务规则处理失效内容和历史版本。
3. 切分内容块（chunk），补充产品、版本、时间、权限等元数据，避免切分后丢失必要上下文。
4. 按检索需要生成向量，建立向量、全文和结构化字段索引。
5. 检查内容质量、索引可用性与权限信息，并维护新增、修改、删除和权限变更。

数据准备不仅是生成向量，还要让系统知道每段内容是什么、来自哪里、属于哪个版本，以及谁能访问。

#### 2. 在线查询：理解问题，找到证据，再组织回答

```text
理解问题，提取关键条件，必要时改写或拆解
  → 选择检索路径，在权限范围内召回候选
  → 融合、去重、重排
  → 组织上下文并校验最终证据权限
  → 依据证据生成回答，提供可核验的引用
```

检索方式取决于信息需求，可以组合全文检索、向量检索、字段过滤、SQL 与 API。需要实时事实时，可在查询过程中调用工具获取，不必全部提前转成向量。

#### 3. 评估反馈：观察各环节，让问题能定位、改进能验证

评估贯穿数据准备、查询和生成，也包括上线前的固定评测集与上线后的运行反馈。根据结果回到对应环节，补数据、调切分、改查询或重排策略，再用同一评测口径验证是否改善。

### 四、传统 RAG 与 Agentic RAG 的区别

- **传统 RAG：** 主要按照预先设计好的流程执行，也可以包含多路检索、改写、融合与重排。
- **Agentic RAG：** 可以根据问题和中间结果，动态决定下一步，例如补搜、换来源、调用工具或结束回答。

区别在于运行时是否能根据结果调整路径，不能简单等同于“一次搜索”和“多次搜索”。自主补搜也应有停止条件、重试次数和成本预算。

### 五、用一个问题理解混合检索

例：“找出 XX 产品 v2.3 文档里关于登录失败的排查方法。”

| 问题中的信息 | 可以采用的处理方式 |
| --- | --- |
| XX 产品、v2.3 | 提取产品和版本字段，作为精确过滤条件 |
| 登录失败的排查方法 | 用向量检索查找语义相关内容 |
| 若还包含具体错误码 | 用全文检索或精确字段匹配，保留原始标识符 |
| 当前用户身份 | 限制允许访问的数据范围 |
| 若还要判断当前服务状态 | 通过业务 API 或结构化查询获取实时信息 |

一种执行方式是在产品、版本与权限限定的范围内，分别进行全文和向量检索，再融合去重、重排，提取回答需要的证据。混合检索并非固定要求“先全文，再向量”。

还要区分“查 v2.3 的文档”和“查文档的版本号”：前者的版本是已知条件，后者的版本是待查询的答案，不能提前拿未知答案做过滤。

### 六、评估时，先看问题发生在哪一层

| 现象 | 需要检查的环节 |
| --- | --- |
| 没找到内容 | 原始资料是否存在、是否完成同步和索引，查询改写与路由是否正确，过滤是否过严 |
| 找到了错误内容 | 版本与实体识别、检索策略、切分质量、排序是否正确 |
| 找到了正确内容，但模型没用上 | 内容是否在重排、压缩或上下文截断中被丢掉 |
| 证据进入上下文，回答仍无中生有 | 生成是否忠于证据，引用能否支持对应结论 |
| 答案事实正确，但业务上不可用 | 适用条件、输出形式、业务规则及用户需求是否满足 |

因此，“检索不到”是排查起点，不能只凭这一现象判定原始数据缺失。有时是检索路径出了问题，也可能是用户本来就无权查看，或知识库确实没有答案。

### 七、指标：快、稳、省、准，以及安全边界

| 维度 | 主要问题 | 指标或验证方式 |
| --- | --- | --- |
| 快 | 响应及时吗，负载能承受吗？ | P50/P95/P99 延迟、吞吐量与并发下表现 |
| 稳 | 服务可靠、数据及时吗？ | 超时率、失败率、降级率、写入后可检索延迟、更新与删除同步情况 |
| 省 | 单次请求及长期运行成本是否可控？ | Embedding、重排、生成调用成本，存储与计算成本，索引构建开销 |
| 准 | 找到的证据和生成的答案可靠吗？ | 检索 Recall、Precision、MRR；答案忠实度、完整性、引用准确性与业务符合度 |
| 安全边界 | 是否发生跨租户或越权访问？ | 权限隔离测试，以及权限变更后缓存、检索和输出的一致性验证 |

P95 延迟表示约 95% 的请求耗时不超过该值。缓存命中率、索引构建时间等是辅助观察指标，要结合延迟、成本和数据新鲜度解释，不能单独代表系统好坏。安全边界应单独验收，不能用更快或更便宜来抵消越权问题。

### 概念校正与补充说明

以下为整理时的助手补充：

1. 传统 RAG 也能复杂、多路、多次检索；Agentic 的关键是根据中间结果动态决策。
2. 数据准备不仅生成向量，也要维护原文、全文和字段索引、权限及更新机制。历史版本是否删除应服从业务需求，过期不等于永远没有价值。
3. 全文检索擅长关键词，但分词不必然保留版本号等标识符的精确语义；严格相等条件优先使用合适的结构化字段或精确匹配配置。
4. 检索失败不能仅凭表象归因，需结合数据覆盖和各节点证据排查。
5. “快、稳、省、准”中的“准”需要独立列出检索与答案质量指标；权限隔离是额外的安全边界。
