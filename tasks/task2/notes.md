## 1. LangChain 框架

LangChain 框架提供了统一的接口，支持模型切换、工具调用和流式处理等，有利于我们重点关注业务逻辑，减少针对某个固定大模型写的适配代码。

可以理解为它封装了很多重复操作，用起来有点像语法糖。比如 Tool Use，如果手动调用，我们需要自己解析模型返回的工具调用信息、执行工具，再把结果包装成消息继续传递给 LLM，还要处理各种错误边界。LangChain 用 `create_agent` 传入模型和 tools，就能把这个基础循环搭起来。不过业务上的异常处理、权限、超时和重试，还是需要自己考虑。

## 2. AI 原生数据库

AI 原生数据库不只是说集成了 AI 的能力，而是围绕 AI 应用的核心数据流，提供可组合、可治理的原生能力，比如统一处理向量、文本、半结构化数据和关系数据等。

在此之前，我们可能需要向量数据库、关系数据库等一起协作，数据同步、权限和查询逻辑分散在不同系统里，流向和交互比较复杂。AI 原生数据库将这些能力整合在一起，提供混合检索，同时保留数据库常规的事务、日志和故障恢复等能力。

### LSM-Tree：前台记录变化，后台批量整理

seekdb 是一种 AI 原生数据库，它的持久化存储采用 LSM-Tree，可以理解为“前台记录变化，后台批量整理”。

写入时，变更会进入内存表 MemTable，并通过 Redo Log 提供持久化保障。满足事务提交条件后，就可以返回成功，不需要等到数据全部整理进磁盘上的 SSTable。之后后台再将冻结的 MemTable 转储为 SSTable，并持续归并整理。

这样比较适合频繁写入的场景。不过不是说 AI 应用都以写入为主，而是记忆更新、文档入库等场景会不断产生新数据。代价是查询可能需要同时查相关的 MemTable 和 SSTable，后台归并也会带来额外的读写和空间开销。

### 融合排名：看谁被更多系统认可，也排得更靠前

不同检索方式的分数量纲不同，不能直接把原始分数相加。比如 RRF 融合排名，主要看文档在各个召回结果里排第几。可以理解为比较谁被更多系统认可、排名也更靠前，而不是谁的嗓门最大。

### 模型调用：先缩小范围，再做重排或生成

对于候选文档的处理，比较稳妥的顺序是：先过滤，再召回，融合并缩小候选集合，最后重排或生成。不要对没有限制的结果集逐行调用模型，而且应该明确并发上限、超时、重试和预算等。

seekdb 提供了 AI 相关函数，可以在 SQL 数据处理流程里调用对应模型，比如生成向量、重排、摘要和抽取等。这里的“数据库内 AI”，可以理解为把模型调用接进数据库的数据流程，模型本身也可以运行在外部服务上。

### Fork / Diff / Merge：让 Agent 先在隔离分支里修改

Fork / Diff / Merge 可以类比 Git 的分支工作流，也有点像用 worktree 开一个独立工作区。基于主数据创建隔离的数据库或表分支，Agent 在分支里修改，不影响主数据。

Diff 可以查看新增、删除、修改和冲突，再由人工或规则判断是否采纳，最后按策略 Merge 回主数据，或者直接丢弃这个分支。
